# AGENTS.md — AGR CLI (`agr`)

Guidance for AI agents working in this repository. This file explains what the
project is, how it is laid out, the core architecture, and the conventions to
follow when reading, modifying, or extending the code. Read it before making
non-trivial changes.

## What this project is

AGR CLI (`agr`) is a Go command-line tool that manages **Tencent Cloud Agent
Runtime (AGR)** resources: instances (sandboxes), tools, API keys, and
data-plane operations such as remote code execution, file transfer, shell/PTY
access, VNC, port forwarding, and mobile ADB tunnels.

- Module path: `github.com/TencentCloudAgentRuntime/ags-cli`
- Go version: `1.25.0` (see `go.mod`)
- Installed command name: `agr` (NOT `ags-cli`)
- Latest stable release: `v0.5.0` (2026-05-22). The `0.5.0` release is a
  breaking change from `0.4.0` — command layout, flags, request input, and the
  JSON/NDJSON output contracts all changed. Revalidate any automation against the
  new surface before upgrading.

Local state lives in `~/.agr/config.toml` (written by `agr init`). It never
creates remote resources.

## Repository layout

```text
cmd/agr/            # main.go — builds the registry, attaches to Cobra, executes
  internal/         # docgen subtool (man page generation)
internal/
  command/          # Registry model: Module, Descriptor, Spec, Deps, Request, Result
  cmdtree/          # Projects the command.Registry into Cobra; flag wiring + validation
  cli/              # Cobra root, AttachCommandRegistry, Execute, version info
  commands/         # One sub-package per leaf command (the bulk of the logic)
    instance/ tool/ apikey/ api/ precacheimagetask/
    registry.generated.go   # GENERATED by cobragen — do NOT edit by hand
  apicli/           # Generated thin wrappers that turn API metadata into commands
  apimeta/          # API metadata catalog, mapping, and generated models (build.go)
  cloudapi/         # Tencent Cloud control-plane API client layer
  controlplane/     # Control-plane orchestration used by commands
  client/           # Shared SDK client construction
  dataplane/        # Data-plane: webshell, pty, proxy, adbtunnel, mobileadb, token, tunnelstore
  output/           # Machine-readable output contracts (envelope, ndjson, exitcode, jq)
  config/           # Config loading (~/.agr/config.toml) + precedence
  iostreams/        # In/out/err stream abstraction
  utils/            # Misc helpers
api/ags/            # API action/meta definitions consumed by apimeta
tests/              # End-to-end "lifecycle" tests (need real credentials)
scripts/            # Helper scripts
```

## Core architecture (read this before editing commands)

The CLI is **registry-driven**, not hand-wired with Cobra commands.

1. **`main.go`** calls `commands.Registry()` to get a `*command.Registry`,
   then `cli.AttachCommandRegistry(registry)` builds the Cobra tree and runs.
2. `internal/command` defines the registry model:
   - A `Module` is the unit of registration: `{ Descriptor, Build func(Deps) (Runtime, error) }`.
   - `Descriptor.Spec` is metadata-only (ID, Path, Use, Args, Flags, Output) and
     is safe to inspect **without credentials**. `Build` is only invoked at
     execution time and receives `Deps` (Config, IO, ControlPlane, DataPlane, etc.).
   - `Request` (normalized inputs) and `Result` (normalized outputs) are the
     contract between Cobra and command handlers.
3. `internal/cmdtree` turns each registered `Module` into a Cobra leaf command
   via `BuildModuleCommand`. It validates descriptors (duplicate names/aliases,
   flag conflicts, generated-vs-workflow flag collisions), wires pflags from
   `Spec.Flags`, normalizes args into a `Request`, runs the handler, and renders
   the `Result` (or propagates a typed `output.CLIError` for exit code).
4. **`commands/registry.generated.go` is generated by `cobragen`.** It imports
   every command sub-package and lists its `Module()`. Do not hand-edit it;
   regenerate it from the codegen tooling. The top-of-file comment says
   "Code generated by cobragen; DO NOT EDIT."

So to add or change a command you edit source in `internal/commands/<group>/...`,
not the generated registry.

## Two kinds of commands

- **Generated API commands (`apicli` / `apimeta`)**: many control-plane commands
  are produced from API metadata in `api/ags` + `internal/apimeta`. The generator
  reads actions, maps them to commands, and emits `api.generated.go` in each
  command folder. `command.Descriptor.Source` is `"apicli"` or `"mixed-api"`.
- **Hand-written workflow commands**: commands with bespoke behavior (temp
  instance lifecycle, streaming, tunnels) live in `command.go` with a `Module()`
  constructor. For a mixed command, `Descriptor.Generated` keeps a snapshot of the
  generated API metadata so cmdtree can detect drift (it forbids changing the
  command ID, path, or API action out from under the generator).

When a command folder contains `api.generated.go`, treat its command surface as
generated; put hand-written overrides in `command.go` and keep them consistent
with the generated `Descriptor.Generated`.

## Adding a new command (convention)

1. Create `internal/commands/<group>/<verb>/` (e.g. `internal/commands/tool/tag/`).
2. Add `command.go` exposing `func Module() command.Module` returning a
   `command.Descriptor{Spec: ...}` and a `Build` that returns a `Runtime` whose
   `Handler` implements `Run(ctx, Request) (*Result, error)`.
3. If it wraps an API action, follow the `apicli` generated pattern (`api.generated.go`);
   otherwise write a workflow `Module`.
4. Register it in `commands/registry.generated.go` (regenerate via cobragen) and add
   any needed `GroupSpec` in the descriptor so `cmdtree` can place it under the
   right parent node.
5. Add unit tests (`command_test.go`) and, for behavior, a `Ginkgo`/`Gomega` spec.
   Use `command_test.go` patterns already present in sibling folders as the template.

## Output contracts (important for automation)

- Non-streaming commands with `-o json` emit one `agr.v1` envelope on stdout:
  `SchemaVersion`, `Command`, `Status`, `Data`, `Failure`, `Warnings`, `Meta`.
- Streaming commands (`instance code run`, `instance exec` with `--stream`)
  emit `agr.events.v1` NDJSON, one JSON event per line (`-o ndjson`).
- `-o json` combined with `--jq <expr>` (via `itchyny/gojq`) extracts a field,
  e.g. `-o json --jq '.Data.InstanceId'`. `--jq` requires `-o json`.
- Exit codes: `0` success, `1` error, `2` usage, `4` auth, `255`
  remote_execution_failed. `instance exec`/`mobile adb` may pass through
  downstream process codes 0–255. See `agr schema -o json --jq '.Data.ExitCodes'`.

## Configuration & endpoints

- Config file: `~/.agr/config.toml` (see `config.example.toml`),
  `[auth] secret_id` / `secret_key` required. Optional: `output`, `region`,
  `domain`, `cloud_endpoint`, `[sandbox] default_user`.
- Precedence: `--flag` > env var > `~/.agr/config.toml` > default.
- Key flags: `--region` (default `ap-guangzhou`), `--cloud-endpoint`
  (control-plane, default `ags.tencentcloudapi.com`), `--domain` (data-plane,
  default `tencentags.com`). Env equivalents: `TENCENTCLOUD_SECRET_ID`,
  `TENCENTCLOUD_SECRET_KEY`, `AGR_OUTPUT`, `AGR_REGION`, `AGR_CLOUD_ENDPOINT`,
  `AGR_DOMAIN`, `AGR_NON_INTERACTIVE`, `AGR_DEBUG`, `NO_COLOR`.

## Build, test, lint

```bash
make build      # go build ./cmd/agr -> ./agr
make test       # go test -v ./...
make lint       # golangci-lint run (.golangci.yml)
make fmt        # gofmt -w .
make e2e        # go test -timeout 20m ./tests/lifecycle/... (needs credentials)
make man        # regenerate man pages via cmd/internal/docgen
```

Run `agr --help` and `agr schema <command> -o json` as the authoritative
reference for the current command surface. The relevant source for the help copy
is each command's `Descriptor.Spec` (`Short`/`Long`/`Examples`).

## Conventions & gotchas

- Keep `Descriptor.Spec` metadata accurate; `agr schema` and `agr --help` are
  derived from it. Wrong metadata misleads both humans and agents.
- Never edit `registry.generated.go` or `api.generated.go` by hand; regenerate.
- Respect the `generated` vs `workflow` flag distinction (see cmdtree
  `validateFlagConflicts`) — do not introduce shorthand/name collisions between
  generated API flags and hand-written workflow flags.
- Tests use `Ginkgo`/`Gomega` (`github.com/onsi/ginkgo/v2`, `gomega`) plus
  standard `testing`. Characterizing tests live in `cmd/agr`.
- `internal/command` is intentionally decoupled from generator layers (it keeps
  `Descriptor.API` opaque `any`) so command metadata can be read without pulling
  in SDK clients — preserve this boundary.

## Where to look for common tasks

- "What commands exist?" → `agr --help`, `internal/commands/*`, `registry.generated.go`.
- "How is command X implemented?" → `internal/commands/<group>/<verb>/command.go`.
- "How is output rendered / exit code set?" → `internal/output/{envelope,ndjson,exitcode,jq}.go`.
- "How is the Cobra tree built / validated?" → `internal/cmdtree/build.go`.
- "Control-plane API call details?" → `internal/cloudapi`, `internal/apimeta`, `api/ags`.
- "Data-plane (tunnel/adb/proxy/pty)?" → `internal/dataplane/*`.
- "Config / auth?" → `internal/config`, `config.example.toml`.
- "Version / changelog?" → `cmd/agr/main.go` (ldflags), `CHANGELOG.md`.
